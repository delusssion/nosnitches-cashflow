# Архитектурные решения

Кратко: дата · решение · почему.

## 2026-10-30 · Ядро расчёта на Rust

Требование эксперта: калькулятор должен работать на огромном числе сделок и экономно расходовать CPU. Ядро — cargo workspace в `engine/`, CLI `cfgen`.

## 2026-10-31 · Начисление процентов — по отрезкам между событиями

Платёж тела внутри процентного периода режет его на секции: каждая секция начисляется на остаток, действовавший в ней («начисление процентов по отрезкам между событиями» из задания). Если эталоны аналитика будут считать по остатку на начало периода целиком — меняется одним местом (`run_timeline` в `engine/crates/cfcore/src/engine/mod.rs`).

## 2026-10-31 · close_payment и хвост начисления

Последнее событие по телу — всегда `close_payment` на весь остаток: после него `principal_after = 0` строго. Перепокрытие явного графика (сделка 20) срезается — собирается ровно остаток; недобор (сделка 54) добирается в `close_payment` в дату погашения (H9). Если даты процентов не доходят до погашения, в дату close добавляется процентный платёж за хвост периода (сделка 55: проценты до 30.06, тело 04.07).

## 2026-10-31 · FLOAT до ветки engine/float

Ставка FLOAT замораживается на дате расчёта (H2+H3): значение индикатора берётся из истории не позже `report_dttm` (`RateSeries::fixing` не «подглядывает» фактические будущие ставки), плюс маржа `interest_rate`, затем floor/cap. События `repricing` появятся в ветке `engine/float`; ANN считается в `engine/ann` (сейчас заглушка — 0 событий).

## 2026-10-31 · ANN: две строки на дату, формула H7, close по факту

Аннуитет `A = B·i/(1−(1+i)^(−n))`, `i = годовая × месяцы периода / 12` (H7), считается один раз от остатка на дату расчёта; пересчёт при репрайсинге — в `engine/float`. В выводе каждая дата аннуитета — две строки: `interest_payment` (начисление по конвенции сделки + накопленные проценты в первой) и `principal_payment = A − проценты`. Проценты считаются по дневной конвенции, а не по `i`, поэтому тело исчерпывается на выплату раньше/позже последней даты сетки (сделка 1: 3,6 млн на 28 лет) — `close_payment` ставится на последнюю фактическую выплату тела, а не по расписанию. Даты платежей: явный список → правило процентов → правило тела (у сделок 1–3 заполнено только оно); единственная дата (bullet) считается как SIMPLE.

## 2026-10-31 · Плавающая ставка: репрайсинг и пересчёт аннуитета

Ставка фиксируется на дате репрайсинга и действует до следующего: индикатор (с лагом, без подглядывания истории за дату расчёта — H3) плюс маржа, затем floor/cap. Событие `repricing` попадает в вывод (amount = 0, rate = новая ставка, base_rate = индикатор); проценты за период, закрывающийся в дату репрайсинга, начисляются по старой ставке (порядок контракта: repricing раньше interest). График фиксированной части (`repricing_dttm_rate_schedule_fixed`) перекрывает маржу у FLOAT и саму ставку у FIXED — по заметке эксперта меняться может и фиксированная часть. Аннуитет (H7) перевычисляется на дате платежа, если ставка изменилась: `A = остаток × i/(1−(1+i)^(−n′))`, `n′` — оставшиеся платежи включая текущий. В спринте 2 будущее индикатора заморожено (H3), поэтому между репрайсингами ставка меняется только через график фиксированной части или лаг, уводящий смотр в прошлое; сценарные сдвиги заработают с кривыми команды 2.


## 2026-10-31 · Движок выровнен по методике и эталонам аналитика

После появления на `main` METHODOLOGY.md (A4) и эталонов (A5) цикл движка переписан под методику, приёмка — тест `engine/crates/cfcore/tests/golden.rs` против 13 эталонов (допуск 0,01 ₽) и команда `cfgen verify`. Ключевые отличия от прежней реализации: даты правил считаются с k=0 (первая дата может быть в месяце начала, §2.2); дата погашения всегда добавляется последней датой процентов и тела (§2.3); проценты прошлого куска периода досчитываются от последней прошлой даты процентов (или `deal_dttm`), либо берутся из поля `accrued_interest`, если оно задано (§4.2, Q13); дата фиксинга FLOAT — последний пересмотр ≤ t, но не раньше даты сделки (§6.2); события `repricing` выводятся только для дат между T0 и Tm; у FIXED события пересмотра — только даты графика фиксированной части; суммы явного графика в одну дату складываются; explicit-график тела используется только у SIMPLE; при исчерпании остатка расчёт сделки останавливается (close ставится в дату исчерпания). Коды ошибок приведены к методике: `UNSUPPORTED_CURRENCY`, `MATURITY_BEFORE_REPORT`, `SCHEDULE_SUM_MISMATCH` (допуск 0,005), `FLOAT_NO_INDICATOR` (error), `FLOAT_NO_REPRICING` (warning, Q14).

## 2026-10-31 · Субсидия — отдельный поток по §7 (H4)

Субсидия есть только при заданном `sub_rate_type_cd`. Ставка: FLOAT — `sub_coeff_index` (пусто → 1) × индикатор (фиксинг на последнем пересмотре субсидии, лаг `sub_indicator_lag_cd`, H3) + `sub_interest_rate`, затем sub_floor/sub_cap; FIXED — только `sub_interest_rate`, индикатор и коэффициент игнорируются (сделки 52/54, Q20). База начисления — остаток тела: путь остатка берётся из клиентских событий. Даты — правило `sub_payment_rule` плюс дата погашения; начисление с последней даты субсидии ≤ T0, а если правило началось после T0 — с его начала (сделка 50). Хвост субсидии за период до закрытия тела платится в дату close, если она не дата субсидии. Флаг `sub_repricing_rule_first_event_flg` не используется (Q3). Проверено эталонами 47 (ANN, ставка 15,5%) и 53 (RGM, 0,9×8%+3,1% = 10,3%).
