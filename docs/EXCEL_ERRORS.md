# Ошибки расчётного файла экспертов

Файл: `testdata/source/experts_calc.xlsx`, лист «1 сделка» — сделка 1: ANN, остаток $B = 3\,646\,037{,}89$ ₽, ставка $r = 7{,}5\%$, конвенция ACT/ACT, дата расчёта 31.08.2022, погашение 15.06.2050, платежи 22-го числа.
Все числа ниже пересчитаны скриптом `analytics/scripts/check_expert_sheet.py` (проверяется тестом `analytics/tests/test_check_expert_sheet.py`).

## 1. Аннуитет по $r/12$, проценты по дням /365 → долг не гасится

**Было.** Платёж считается по месячной ставке (B14):

$$A = B \cdot \frac{i}{1 - (1+i)^{-n}}, \qquad i = \frac{r}{12}, \quad n = 334,$$

а проценты каждого периода — по фактическим дням (F19…F352):

$$I_k = B_{k-1} \cdot r \cdot \frac{d_k - d_{k-1}}{365}, \qquad P_k = A - I_k .$$

Периоды разной длины (28–31 день, последний — 24 дня: 22.05.2050 → 15.06.2050), поэтому $\sum_k P_k \ne B$.

**Эффект.** После последнего платежа остаётся непогашенный долг $B_{334} = 15\,420{,}45$ ₽ (ячейка E352).

**Как правильно.** Последнее событие по телу — `close_payment` на весь остаток: $P_n = B_{n-1}$, после него остаток строго 0 (контракт, формат 3).

## 2. Конвенция ACT/ACT, а в формулах всегда /365

**Было.** В сделке `day_convention_cd = ACT/ACT`, но в формулах процентов делитель 365 (F19: `=$F$3*$J$3*((B19-B17)/365)`), в том числе для дней високосных лет.

**Как правильно** (ACT/ACT ISDA, гипотеза H5): период режется по границам календарных лет,

$$\tau(d_1, d_2) = \sum_{y} \frac{\text{дни периода в году } y}{365 \text{ или } 366}.$$

**Эффект** (тот же аннуитет, последний платёж закрывает остаток):

| Расчёт | Проценты за срок, ₽ |
|---|---|
| /365, как в файле | 5 065 848,11 |
| ACT/ACT ISDA | 5 051 623,47 |
| Разница | **≈ 14 224,63** |

Без закрывающего платежа ISDA-график тоже не гасится до нуля: остаётся 1 195,82 ₽.

## 3. Число платежей и бакеты вбиты вручную

**Было.** Число оставшихся платежей B15 = `334` — константа; все 334 даты платежей (B19:B352) — константы; бакет каждой строки (колонка I) — прямая ссылка на заголовок (`=$C$5`, `=$D$5`, …), выбранная вручную, а не по сроку из колонки H.

**Эффект.** При смене даты расчёта, срока или параметров сделки лист молча считает неверно: число платежей, даты и бакеты не пересчитываются.

**Как правильно.** Даты строятся из правил сделки (`regular_payment_rule_*`, `maturity_dttm`), число платежей — их количество после даты расчёта; бакет — функция срока до платежа.

## 4. Лист «Портфель 5 сделок»: `#REF!`

**Было.** У 4 из 5 сделок (16, 29, 33, 44) все формулы ссылаются на удалённые листы: `=#REF!`, `=SUM(#REF!)`. Итог портфеля не считается.

**Как правильно.** Портфель считается тем же алгоритмом по всем сделкам из CSV, без ручных листов на каждую сделку.

## Что сделано правильно

- **Аннуитет пересчитан от остатка на дату расчёта:** $A = \text{PMT}(r/12,\ 334,\ 3\,646\,037{,}89)$, а не от первоначальной суммы.
- **В первый будущий платёж включены проценты, накопленные до даты расчёта:** период начисления первого платежа — с последней выплаты 22.08.2022 по 22.09.2022:
  $I_1 = 3\,646\,037{,}89 \cdot 0{,}075 \cdot \frac{31}{365} = 23\,224{,}76$ ₽.

## Как это учтено в нашем движке

| Ошибка | Как учтено |
|---|---|
| Долг 15 420,45 ₽ после графика | Последнее событие тела — `close_payment` на весь остаток; инвариант «остаток после последнего события = 0» проверяется тестами эталона и сверкой |
| /365 вместо ACT/ACT | Доля года считается по `day_convention_cd` сделки; ACT/ACT = ISDA (H5); контрольное число сделки 1 — 5 051 623,47 ₽ |
| Ручные даты и число платежей | Даты строятся генератором из правил периода, `day_num`, явных списков; будущие — строго после даты расчёта (H6) |
| `#REF!` в портфеле | Один алгоритм для всех сделок портфеля, ошибки сделок — в `errors.csv`, остальные считаются |
